# Platform Error-Handling Update

Status: Completed on 2026-07-22.

Current-policy note (2026-07-29): the dialog-specific direct-return and throwing
clauses in this historical roadmap are superseded. Every public dialog operation
is now `noexcept`. The three submission methods and `DialogShutdown` are
Result-bearing exception shields that catch and log ordinary exceptions, roll
back partial state as needed, and return `BackendFailure`. A caught platform
exception retains its original formatted message and embedded platform code as
diagnostic text; no message parsing or typed platform exception is introduced.
`DialogShutdown` may also return `InvalidArgument` directly while requests are
outstanding. The five
pending-state and completion observers return direct values under documented
preconditions. Asynchronous `DialogFailure` remains outcome data. Platform and
event timing now use `ponder::core::Timestamp::Now()` exclusively; platform code
never calls `SDL_GetTicksNS()`.

Current lifecycle note (2026-07-30): callback-based creation clauses below are
also superseded. `Runtime::Create()` is argument-free, validates the
process-entry thread, acquires the single-runtime reservation, and returns an
uninitialized owner without constructing `RuntimeImpl`. Callers configure typed
hints directly and then call `Runtime::Initialize()` with application metadata;
the first hint operation or `Initialize()` lazily constructs `RuntimeImpl`, whose
construction verifies SDL's main-thread and exclusive-lifecycle requirements.
`Initialize()` validates metadata and initializes the backend. There is no templated
pre-initialization callback overload.

Historical scope note: this completed failure-policy roadmap intentionally
preserved the then-current `pond::platform` namespace. The independent
2026-07-23 namespace-and-timing migration supersedes those preservation clauses:
the current namespace is `ponder::platform`, and public platform declarations
use `ponder::core::Timestamp` and `ponder::core::Duration` directly without a
platform timing forwarding header or aliases. A later 2026-07-23 exception
contract update also supersedes the typed platform-exception clauses below:
platform now throws `ponder::core::Exception`, and `PLATFORM_EXCEPTION` embeds
the formatted `PlatformErrorCode` in its message. Task text below is retained
as a record of the constraints in force when the work was performed.

A later 2026-07-23 lifecycle and test-seam cleanup, further amended by the
explicit lifecycle above, supersedes task clauses that
prescribed distinct creating, active, and destroying slot states,
production-only stage hooks, provider injection, or
`IPlatformRuntimeBackend`. The private atomic 0/1 reservation remains held from
`Runtime::Create()` until owner destruction and permits sequential recreation
after release. The first hint operation or `Runtime::Initialize()` lazily
constructs the selected non-virtual `RuntimeImpl`: production uses `SdlRuntime`, while the isolated mock executable
uses `MockRuntime` through its compile-time source variant and does not link
`ponder::platform`. Tests use fixture-owned mock state
and verify observable rollback instead of mutating global production hooks or
overrides. The completed task text below is retained unchanged as a historical
record.

This roadmap migrates `libs/platform/` to the core failure policy established by
[ADR 0012](../../../docs/adr/0012-core-namespace-and-failure-policy.md) and the
platform-specific contract established by
[ADR 0013](../../../docs/adr/0013-platform-failure-policy.md). It is written as a
sequence of implementation tasks that can be handed to Codex one at a time.

Intermediate tasks may leave later tasks or examples uncompilable. Do not add
temporary compatibility APIs merely to keep every intermediate revision green.
The library convergence task must restore all platform builds and automated
tests before the example work begins. The final task must leave the platform
library, platform tests, and all four platform examples building, with all
automated checks passing and available host/manual checks recorded accurately.

## Scope

In scope:

- `libs/platform/`, its public headers, private implementation, and active docs.
- `tests/unit/platform/` and `tests/integration/platform/`.
- The four examples under `examples/platform/` and their documentation.
- The core namespace and exception compatibility changes required by the
  completed core migration.

Out of scope:

- `libs/render/`, `libs/ui/`, `examples/render/`, and `examples/ui/`.
- New platform features or general API redesign.
- Renaming the existing public `pond::platform` namespace. This roadmap migrates
  removed `pond::core` references to `ponder::core` but preserves the platform
  namespace under the task-specific public-API constraint.
- Changing public include paths or the `ponder_platform` / `ponder::platform`
  CMake target names.

Public API changes are limited to changes that express the new failure policy:
direct return types, `void`, `optional`, retained `Result` contracts, and correct
`noexcept` declarations. The `pond::platform` namespace, names, ownership,
descriptors, event types, and behavior unrelated to failure handling remain
stable. A whole-project namespace migration requires a separate decision.

## Failure Policy To Implement

### Exceptional failures

Throw for failures that should never or only rarely occur and for which the
current operation's caller cannot complete a useful recovery. This includes:

- runtime or window construction failure;
- SDL initialization and ordinary backend query/mutation failure, except for
  the explicitly retained external-service and capability outcomes below;
- invalid lifecycle phase, wrong-thread use, moved-from use, and broken
  invariants;
- invalid descriptors and forged closed-enum values;
- unsupported ordinary window, cursor, hint, or dialog operations; and
- malformed backend data that violates the platform abstraction's contract.

Platform failures that need a stable discriminator throw
`ponder::core::ExceptionWithData<pond::platform::PlatformErrorCode>`,
constructed at the failure site with `PONDER_EXCEPTION_WITH_DATA`. Use
`PONDER_EXCEPTION` for exceptional failures that do not need a platform code,
and use `PONDER_ASSERT`, `PONDER_VERIFY`, or `PONDER_UNREACHABLE` only according
to their documented invariant contracts. Do not reintroduce `ThrowException`
or create a new public platform exception class.

Wrong-thread public calls throw a typed exception carrying
`PlatformErrorCode::WrongThread`. Invalid descriptors and forged enum inputs
carry `PlatformErrorCode::InvalidArgument`. Backend/capability failures on
direct APIs likewise carry their typed platform code.
Moved-from use and impossible internal invariants remain release-active
`PONDER_VERIFY` failures and therefore throw the plain
`ponder::core::Exception` base. Reserve `PONDER_UNREACHABLE` for branches that
are impossible after validation. Tests must check a platform payload only for
typed platform failures.

An SDL error string must be copied immediately after the failed SDL call and
before any other SDL call. The typed exception or retained
`ponder::core::Error` must include the operation and relevant
runtime/window/display context. Diagnostic text is never parsed for control
flow.

### Value-based failures

Retain `Result<T>` only when the failure is a normal input, capability, or
external-state outcome and the caller or its immediate caller has a concrete
recovery such as retrying, refreshing topology, falling back, or reporting a
user-facing problem.

A retained-`Result` function may still throw. Programming errors, lifecycle
violations, and unexpected backend corruption are exceptional even when the
same function returns `Result` for an expected outcome. Do not catch an
exception merely to repackage it as `ponder::core::Error`.

The intended public `Result` surface is exactly these eleven operations:

| API | Expected value-based failures | Immediate recovery |
| --- | --- | --- |
| `ClipboardManager::GetClipboardText` | unavailable, unsupported, malformed external text, or access failure | disable paste or retain local text |
| `ClipboardManager::SetClipboardText` | invalid input, unavailable, unsupported, or access failure | sanitize input or offer another copy path |
| `PlatformRuntime::GetDisplayInfo` | stale nonzero `DisplayId` (`NotFound`) | re-enumerate displays |
| `PlatformRuntime::SetMouseCapture` | unsupported or rejected host capability | continue without global capture |
| `PlatformRuntime::GetGlobalMousePosition` | unsupported or unavailable global coordinates | use window-relative input |
| `PlatformRuntime::OpenExternalUri` | invalid user-provided URI or host launch/capability failure | show or copy the URI |
| `Process::Wait` | child/wait operating-system failure | retry or report process failure |
| `Process::Terminate` | graceful/forced termination failure | retry or escalate termination |
| `LaunchProcess` | invalid executable/input or operating-system launch failure | correct, retry, or report |
| `Window::GetNativeHandle` | incompatible graphics mode or unsupported native driver | select another rendering path |
| `Window::GetDisplayId` | transiently unresolved/disconnected display | wait for topology or retry |

Each implementation task must narrow these functions to their documented
value-based errors. For example, `GetDisplayInfo` returns `NotFound` for a stale
nonzero ID, throws `InvalidArgument` for a zero/invalid ID, and throws
`BackendFailure` for a corrupt backend response. A wrong-thread call throws a
typed platform exception even if its return type is `Result`; moved-from use
fails the release-active core verification contract.

Clipboard and URI text classifications are exact:

- An empty clipboard string is a successful value and setting an empty string
  succeeds.
- Invalid UTF-8 or an embedded null passed to `SetClipboardText` returns
  `InvalidArgument` because the immediate caller can sanitize or reject the
  input.
- Unsupported/unavailable clipboard access and invalid text received from the
  host return `Unsupported` or `BackendFailure`. They do not throw.
- Empty, invalid UTF-8, or embedded-null URI input returns `InvalidArgument`.
  Unsupported URI service and host launch failure return `Unsupported` or
  `BackendFailure`.
- Wrong-thread, moved-from, and broken-lifecycle use follow the exception and
  verification rules above for both services.

`DialogOutcome` remains
`variant<DialogSelection, DialogCancellation, DialogFailure>`. Completion
happens after the initiating stack is gone, so asynchronous dialog failure stays
event data in `DialogFailure{ponder::core::Error}`. This is not permission to
retain `Result` for synchronous dialog submission.

### Direct and optional public APIs

The following public contracts are the target:

- `PlatformRuntime::Create` returns `PlatformRuntime`.
- `PlatformRuntime::CreateWindow` returns `Window`.
- `PlatformRuntime::EnumerateDisplays` returns `vector<DisplayInfo>`.
- `PlatformRuntime::SetSystemCursor`, `ShowCursor`, and `HideCursor` return
  `void`.
- Every `HintManager::PushHint`, `PopHint`, and `ClearHints` overload returns
  `void`.
- Every `HintManager::GetHint` overload returns `optional<hints::Type>`. An
  unset hint is ordinary absence; malformed hint text throws.
- `DialogManager::ShowOpenFileDialog`, `ShowSaveFileDialog`, and
  `ShowOpenFolderDialog` return `DialogRequestId`.
- `DialogManager::Shutdown` returns `void`.
- All `Window` operations that currently return `Result` or `VoidResult` become
  direct values or `void` except `GetNativeHandle` and `GetDisplayId`.

The existing direct observers, IDs, descriptors, event representations,
ownership model, and move-only contracts remain unchanged.

### Exception and `noexcept` boundaries

- No C++ exception may escape an SDL C callback, an operating-system callback,
  a thread entry point, or a destructor.
- Destructors, move operations, and release paths remain `noexcept` and perform
  best-effort cleanup with diagnostics where recovery is impossible.
- Do not add `noexcept` to a newly direct API merely because `Result` was
  removed. SDL calls, allocation, verification, and exception construction can
  still throw.
- Preserve the current `ToErrorCode` and public enum-name helper signatures and
  diagnostic fallback behavior. Redesigning those helpers is unrelated to this
  Result-to-exception migration.
- `DisplayOrientation::Unknown` is valid runtime data. It must not be confused
  with a forged enum value.
- Audit every `noexcept` function that calls `PONDER_VERIFY` or a newly throwing
  helper. Operational failures at a destructor, move-release, callback, or
  thread boundary must be caught and contained. Existing release-active
  verification of impossible ownership/thread invariants at those boundaries
  remains an intentional termination contract. Ordinary helpers that can now
  throw lose `noexcept`.

## Rules For Every Task

- Read the root `AGENTS.md` and `libs/platform/docs/Codex.md` before editing.
- Preserve SDL encapsulation, one-runtime ownership, owner-thread affinity,
  strong IDs, staged window creation, display-map consistency, event ordering,
  and no-throw destruction.
- Update the production code, mocks/fakes, header self-containment coverage,
  and focused tests owned by the task.
- Verify the documented exception type, and verify `PlatformErrorCode` payload
  only for typed platform failures. Also check message context, source location,
  rollback, and subsequent usability. Do not only replace `HasValue()`
  assertions with broad `EXPECT_THROW` checks.
- Keep `ponder::core::Error` and `ToErrorCode` only in approved `Result` and
  asynchronous-outcome paths.
- Remove obsolete `Result.hpp` includes and propagation macros as their last use
  disappears from a file.
- Do not change render or UI code to make an intermediate build pass. Set
  `PONDER_BUILD_RENDER=OFF` and
  `PONDER_BUILD_UI_RENDER_INTEGRATION=OFF`, or build only explicit platform
  targets.
- If a task intentionally leaves a known compile failure for a later task,
  record the exact target and cause in its handoff. Never hide the failure with
  a broad test skip.
